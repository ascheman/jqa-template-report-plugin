The template-report plugin is a jQAssistant `ReportPlugin` that renders rule results through https://freemarker.apache.org/[FreeMarker] templates.
It registers under the report id `template`.
The plugin looks templates up filesystem-first, class-path-fallback: by default a project-local directory `jqassistant/templates/` wins over `/templates` on the plugin class loader.
Templates can live next to the rules in a Maven project, in a sibling concept-plugin, or anywhere on the jQAssistant plugin class loader's `/templates` resource path.

The default output format is AsciiDoc (file extension `.adoc`), but the renderer is text-format-agnostic.
Switching to Markdown, Confluence storage format, or anything else means writing different templates -- no code change.

== Report Id and Activation

A consumer rule activates the plugin by declaring it as a report type:

[source,xml]
----
<concept id="my:BundleMetadataReport">
  <description>Bundle metadata as an AsciiDoc fragment.</description>
  <cypher><![CDATA[
    MATCH (b:Osgi:Bundle)
    RETURN b.bundleSymbolicName AS SymbolicName,
           b.bundleVersion      AS Version
    ORDER BY SymbolicName
  ]]></cypher>
  <report type="template" primaryColumn="SymbolicName"/>
</concept>
----

If `primaryColumn` is omitted, the plugin renders a single file per rule containing all rows.
If `primaryColumn` is set, the plugin groups rows by that column's value and renders one file per group.

== Output Layout

All output goes under the configured jQAssistant report directory, in a `asciidoc/` subdirectory:

[options="header"]
|====
| Mode | Output Path
| Single-file (no `primaryColumn`)  | `<reportDir>/asciidoc/<rule-id>.adoc`
| Per-group (with `primaryColumn`)  | `<reportDir>/asciidoc/<keyValue>/<rule-id>.adoc`
|====

`<rule-id>` is the rule's identifier with colons escaped to underscores, e.g., `osgi_BundleMetadataReport`.
`<keyValue>` is the primary column value with characters outside `[A-Za-z0-9._-]` replaced by `_`.

== Template Lookup

For a rule with id `group:RuleName`, the plugin looks for a template named:

[source]
----
group-RuleName.adoc.ftl
----

Colons in the rule id become hyphens; the suffix is configurable (see `template.template-suffix`).
The plugin checks two layers, in order:

. *Filesystem* -- `<template.template-dir>/<name>`, where `template.template-dir` defaults to `jqassistant/templates` and resolves relative to the JVM working directory.
  Under Maven that is the project root.
. *Plugin class loader* -- `/templates/<name>` on the thread context class loader, which under jQAssistant's plugin loader sees every loaded plugin's resources.

If both layers contain the same name, the filesystem copy wins.
That gives you two complementary options for shipping templates:

* Drop them into your project under `jqassistant/templates/` -- no plugin JAR required.
* Package them in a JAR alongside your rules (under `/templates/` in the JAR) and declare that JAR as a jQAssistant plugin.

When neither layer has a match, the plugin skips the rule with a debug log only.
A rule set can mix `template` with other report types and only ship templates for the rules that need them.

[TIP]
====
Putting a same-named file under `jqassistant/templates/` overrides a plugin-shipped template for a single project, without rebuilding the plugin JAR.
Handy for tweaking wording, adding annotations, or swapping output format on a per-project basis.
====

=== Worked Example: Project-Local Templates

The default layout assumes a Maven project that consumes jQAssistant.
Drop the template next to the rule -- no plugin JAR, no extra configuration:

[source]
----
my-project/
├── .jqassistant.yml                                        <1>
├── jqassistant/
│   ├── my-rules.xml                                        <2>
│   └── templates/
│       └── my-BundleMetadataReport.adoc.ftl                <3>
├── pom.xml
└── src/
----
<1> Declares this plugin under `jqassistant.plugins`.
<2> Rule definition with `<report type="template" primaryColumn="SymbolicName"/>`.
<3> Template name derived from the rule id (`my:BundleMetadataReport` -> colons replaced by hyphens) plus the suffix `.adoc.ftl`.

Running `mvn jqassistant:analyze` renders one file per `SymbolicName` group under `target/jqassistant/report/asciidoc/<SymbolicName>/my_BundleMetadataReport.adoc`.

== Data Model Exposed to Templates

[source]
----
rule    -> { id, description, severity }
columns -> List<String> of column names
rows    -> List<Map<String, String>> of column-name to label-string
key     -> String, only set in per-group mode (= the group's primary column value)
----

A typical FreeMarker template:

[source,asciidoc]
----
[#ftl encoding="UTF-8"]
[#assign sym = key!"(unknown)"]
[[my-${sym}-metadata]]
== Metadata - ${sym}

[#if rows?size == 0]
NOTE: No metadata recorded.
[#else]
[options="header",cols="1,3"]
|===
| Property | Value
[#list rows as row]
| Symbolic Name | ${row.SymbolicName!"-"}
| Version       | ${row.Version!"-"}
[/#list]
|===
[/#if]
----

Always handle the empty-rows case explicitly.
See <<pitfalls>> for why.

== Configuration Properties

Each property below can be set globally in `.jqassistant.yml` under `jqassistant.analyze.report.properties.*`, or per-rule via the rule's `<report><properties>...</properties></report>` element.
Per-rule values override global values; an explicit empty per-rule value disables the feature for that rule.

[options="header",cols="2,1,1,3"]
|====
| Key                              | Type     | Default          | Effect
| `template.output-subdir`         | string   | `asciidoc`       | Subdirectory under `<reportDir>/` where rendered files land.
| `template.output-suffix`         | string   | `.adoc`          | Filename suffix for rendered files (include the leading dot).
| `template.template-suffix`       | string   | `.adoc.ftl`      | Suffix appended to the rule id when looking up the template on the classpath.
| `template.report-label`          | string   | `AsciiDoc`       | Human-readable label registered with jQAssistant's report context (shown in the master report listing).
| `template.primary-key-pattern`   | regex    | (none)           | In per-group mode, drops groups whose primary column value does not match.
| `template.stub-source`           | rule id  | (none)           | Renders empty-row stubs for keys present in the named rule but missing in the current rule.
| `template.template-dir`          | path     | `jqassistant/templates` | Filesystem directory checked before the class path. Relative to the JVM working directory. An explicit empty string disables the filesystem layer.
|====

For the output-format properties (subdir, suffixes, label) an empty per-rule value falls through to the global value -- there is no meaningful "disabled" state.
For the filter and stub-source, an explicit empty per-rule value disables the feature for that rule even when the global value is set.

=== Switching Output Format

To render Markdown instead of AsciiDoc:

[source,yaml]
----
jqassistant:
  analyze:
    report:
      properties:
        template.output-subdir: "markdown"
        template.output-suffix: ".md"
        template.template-suffix: ".md.ftl"
        template.report-label: "Markdown"
----

Then ship `.md.ftl` templates instead of `.adoc.ftl` ones.
The renderer is text-format-agnostic; only the data model and the FreeMarker engine constrain what your templates can produce.

=== Choosing the Template Directory: `template.template-dir`

The default `jqassistant/templates` matches the project-local convention shown in <<_worked_example_project_local_templates>>.
To keep templates somewhere else (for example, under `src/`):

[source,yaml]
----
jqassistant:
  analyze:
    report:
      properties:
        template.template-dir: "src/jqassistant/templates"
----

Relative paths use the JVM working directory as base, so `src/jqassistant/templates` lands at the project root under Maven.
Absolute paths work too.
Setting the value to an explicit empty string disables the filesystem layer entirely, leaving the class path as the only source of templates.

=== Filtering: `template.primary-key-pattern`

Common case: limit per-bundle / per-module output to the rows the consumer cares about.

[source,yaml]
----
jqassistant:
  analyze:
    report:
      properties:
        # only render fragments for the consumer's own bundles
        template.primary-key-pattern: "com\\.example\\..*"
----

An invalid regex is logged once and ignored -- the build does not fail.

=== Stubs: `template.stub-source`

A second rule's primary-column values define the _universe_ of expected keys.
Any rule that does not produce a row for one of those keys gets an empty fragment rendered with `rows = []`, so the section heading and anchor still appear.

This keeps consumer-side AsciiDoc `include::` directives uniform across the universe -- every key has every section's fragment, even if some are stubs.

[source,yaml]
----
jqassistant:
  analyze:
    report:
      properties:
        template.stub-source: "my:BundleMetadataReport"
----

[[mental-model]]
==== Mental Model

. The universe of keys is _not_ read from the graph; it is whatever the named universe-source rule produced as primary-column values during _this_ analyze invocation.
. Cypher queries do not consult each other.
  Cross-rule communication happens entirely through this plugin's in-memory map: as each rule's result is delivered, the plugin records the keys that survived the filter; later rules look them up.
. Therefore the named universe-source rule must run _before_ any rule that uses it as stub source.
  Enforce with `<requiresConcept refId="..."/>` in the rule XML.
  If a rule references a stub source that has not been processed yet, a `WARN` is logged and stubs are skipped for that invocation.
. A rule using itself as the stub source is a no-op (skipped); by construction every key in the universe trivially has a row in the rule that defined the universe.
. The `primary-key-pattern` filter is applied _before_ keys enter the universe.
  The universe is the filtered key set, not the raw graph state.

==== Event Order in a Single Analyze Invocation

[source]
----
1. jQA executes ruleA (the universe source, ordered first via <requiresConcept>)
2. ruleA's Result is handed to TemplateReportPlugin.setResult(...)
3. plugin renders one fragment per row + records seenKeys[ruleA.id] = {observed keys}
4. jQA executes ruleB (a section that uses ruleA as stub source)
5. plugin groups ruleB's rows by primaryColumn; renders real fragments for each group
6. plugin reads template.stub-source on ruleB → ruleA.id
7. plugin computes (seenKeys[ruleA.id] - ruleB's groups) and renders an empty stub
   (rows = [], key = ...) for each missing key, using ruleB's template
8. ... repeat for every subsequent rule
----

[[pitfalls]]
== Known Pitfalls

=== Empty Tables in Stubs

A template that does

[source,asciidoc]
----
[options="header"]
|===
| Property | Value
[#list rows as row]
| ...
[/#list]
|===
----

renders a section heading followed by a header-only empty table when `rows` is empty.
Most readers find that confusing.

[TIP]
====
Always wrap the table in a guard:

[source,asciidoc]
----
[#if rows?size == 0]
NOTE: No items.
[#else]
[options="header"]
|===
...
|===
[/#if]
----

In stub mode the plugin invokes the template with `rows = []` -- the guard's else branch is the rendered fragment.
====

=== Forgetting `<requiresConcept>`

A rule that declares `template.stub-source` without a corresponding `<requiresConcept>` may run before the source rule has been processed.
The plugin logs:

[WARNING]
====
`Rule '...' configured template.stub-source='...', but that rule has not been processed yet (forgot a <requiresConcept>?). Skipping stubs.`
====

The build does not fail, but no stubs are produced for that rule in that invocation.
Adding the `<requiresConcept>` is enough to fix it.

=== jQAssistant Config Ordinal Trap

Properties from `.jqassistant.yml` are loaded at SmallRye Config ordinal 100, while Maven `-D` system properties are exposed at ordinal 90.
Anything set in `.jqassistant.yml` therefore _cannot_ be overridden via the Maven command line.
To change a value temporarily, edit the YAML or pass it via the jQAssistant Maven plugin's `<yaml>` parameter.
